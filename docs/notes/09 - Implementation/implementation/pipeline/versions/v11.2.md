# v11.2 - Heterogeneous Micro-Macro Search (the split path)

> **Status:** DESIGN (idea frozen 2026-06-18; implementation plan + overnight probe next) | **Topic:** a redesign that unifies family selection + depth/width + per-stage ops into ONE micro-macro search over a heterogeneous (cross-family) operation space, evaluated multi-fidelity (cheap prune -> expensive verify). The "break out of the small-space cap" bet. | **Related:** [[v11]], [[v10]], [[EGNAS]], [[DARTS Family]], [[2022 - BLOX Macro NAS Benchmark]], [[Pipeline v10 - Design + Idea Ledger]]

## The split: two paths for v11

v11 forks. We keep both; v11.2 is the high-risk/high-reward path, and if it does not beat v10 we fall straight back.

- **v11 (incremental, safe):** v10's robust core + the gated verified per-stage macro-attention + a properly-gated cross-family ensemble. Small, bounded upside (Chesseract-type wins). Documented in [[v11]].
- **v11.2 (redesign, this note):** one heterogeneous micro-macro search that replaces the `fingerprint -> family gate -> depth -> width -> macro-op` chain with a single search. The bet that breaks the small-space ceiling. **Fallback:** if it does not beat v10 on a fair test, we abandon it and keep improving v10/v11.

## Why (the reasoning that got us here)

1. **The CIFARTile gap.** v10 scores 73.7% on CIFARTile; PC-DARTS scores 92.3%. PC-DARTS searches a conv space *deep* (~20 layers); we cap depth at 8. We **under-searched depth**, especially on image-like data.
2. **Breadth bought at the cost of depth.** We spread the search across families (conv / 1-D TCN / 2-D TCN) but searched each one *shallowly* (depth {4,6,8}, width {32,48,64}). EGNAS and the benchmark winners commit to *one* space and search it *thoroughly*. On encoded data our family routing is competitive; on image data the shallow conv search cost us.
3. **Our "families matter" thesis was never tested against a strong conv search.** "tcn2d beats conv" was measured against our own *shallow reimplemented* conv/EGNAS baselines. A properly deep conv search might beat our multi-family pipeline. We do not actually know. (And our EGNAS reimpl is suspected slightly wrong; real EGNAS beats v10 on Cryptic, the decisive 2025 dataset.)
4. **BLOX:** heterogeneous-block nets Pareto-dominate uniform stacks (real headroom), but block proxies are unreliable -- "directly search for a model that performs well when fully trained." That is our verify philosophy.
5. **Overfitting / generality.** A search that *decides* the architecture from the data is **more general** (less hand-engineered) than our fingerprint->family->grid heuristics. Ironically our "generality" may be the more bespoke, more overfit thing. The blind custom datasets ([[Sedol]] etc.) remain the honest hold-out for any v11.2 claim.

## The design (structure)

One search, three pieces:

- **Macro = depth + width, searched thoroughly (including DEEP, ~16-20).** Fixes the cap that cost CIFARTile.
- **Micro = each stage picks an op from the FULL cross-family vocabulary** (plain conv, dilated/2-D-TCN, 1-D-TCN, SE, spatial attention, recurrent) -> genuinely **heterogeneous** stages (conv -> conv -> attention -> tcn ...), the BLOX headroom. This *replaces* the family gate: "which family" becomes "which op per stage," decided by search.
- **Multi-fidelity evaluation (the crux).** The heterogeneous space is enormous (|ops|^depth x widths) -- you cannot full-train every candidate. So:
  - **Cheap rung** (short-train, or a small one-shot supernet over the op space) -> used ONLY to **prune** to a shortlist. Unreliable, never committed on.
  - **Expensive rung** (full-train + **verify-before-adopt**) -> runs only on the shortlist, makes the **committed** decision.
  - This is Hyperband / successive-halving applied to a heterogeneous micro-macro space = EGNAS's *structure* + BLOX's *full-train-the-finalists discipline* + our *verify* reliability.

## Hybrid: budget-gated deployment (the actual shape)

v11.2 is NOT a replacement for v10 -- it is a **high-budget tier bolted onto v10's existing budget-graceful pipeline.** v10 already degrades by the clock (skip the searches under ~35 min, skip the aug probe under ~15 min, train-to-budget). The heterogeneous micro-macro search slots in as the *top* tier:

- **Low budget (e.g. < ~1-2 h):** v10's fast, proven route -- fingerprint -> family default (tcn2d / conv) -> train to budget. Unchanged, robust, cheap. This is the safety floor.
- **High budget (e.g. 2 h+ / 4 h+):** the heterogeneous micro-macro search (multi-fidelity prune -> verify) runs, because only then is there time to prune *and* verify honestly. Its result is adopted only if it beats the v10-route arch (verify-before-adopt at the top level too).

So the expensive search can never hurt a tight-budget dataset, and on generous budgets it is gated by the same beat-the-default rule as everything else. This also matches the competition reality: budgets vary per dataset, and the pipeline should spend search effort only where the clock allows. The exact thresholds are tuned from the timing logs (we already log `search_seconds` per dataset) and the overnight probe.

v11.2 moves us **up** the map (bigger space than v10's tiny grid) while staying **right** (high fidelity). The trick is the two rungs: the cheap rung lives top-left (big space, cheap, unreliable) but only PRUNES; the expensive rung lives bottom-right (verified) and only COMMITS. We never trust the cheap rung's ranking -- the exact failure (proxy wall) that beats naive EGNAS/DARTS.

## Hardware-agnostic by design (hard requirement)

The submission runs on the organisers' UNKNOWN hardware (GB10 / A100 / B300 / anything) under a wall-clock budget. Nothing may assume a GPU. Two modes, both hardware-blind:

- **Comparison (search internals):** epoch-based, never wall-clock. The same candidates at the same epochs train identically on any GPU, so rankings and the winner are hardware-independent. This is why the dev probe is portable -- "GB10 overnight" is only *where* we run the experiment, not an assumption in the code.
- **Deployment (runtime budget allocation):** the search sizes itself to the wall-clock budget by SELF-CALIBRATING on whatever GPU it lands on -- run a calibration epoch, measure observed per-epoch seconds, then choose how many candidates and epochs-per-rung fit the remaining clock. Fast GPU -> deeper search; slow GPU -> shallower; identical code. This is v10's existing train-to-budget mechanism (the trainer re-anchors its cosine schedule to observed wall-clock after epoch 0) generalised to the search. The `cap_s` wall-clock guard is a safety only and must never truncate an arm in normal operation (that would make a result hardware-dependent -- we log if it ever fires).

## The core tension and risks

- **The whole design hinges on the cheap prune being *good enough* to shortlist the right candidates.** If the cheap rung's ranking is so bad the true winner never makes the shortlist, multi-fidelity fails. This is the proxy wall, now controlling *recall of the shortlist* rather than the final pick.
- **Compute.** The expensive verify over a shortlist is hungry -> the *full* v11.2 is **cluster-era** (A100s), not the GB10.
- **Recurrent / attention ops are slow and unstable to train inside a search** (the v7 lesson: an SGD proxy cannot train an LSTM well). The vocabulary may need per-op training care.
- **Dependence on the CIFARTile depth test (running now):** if depth alone closes CIFARTile, a thorough *conv-only* deep search may suffice and the cross-family heterogeneity is gravy; if not, the heterogeneous family search is the justified bet.

## Scope / plan

- **Overnight GB10 probe (next):** a minimal heterogeneous micro-macro search on a few datasets (e.g. CIFARTile + Chesseract + one encoded) to get first signal: does the unified heterogeneous search beat v10's per-dataset arch on a fair, fully-trained comparison? Queue after the depth=20 run.
- **If promising:** build the full multi-fidelity version on the cluster.
- **If not:** fall back to v11 / improving v10. No sunk-cost.
